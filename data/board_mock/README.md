# 토의보드 모의 데이터 (갈무리 방법 검토용)

10/14 리더 토론세션에서 58개 반조(1A…29B)가 8개 항목에 **전부** 답했다고 가정한 모의 데이터다.
AI 요약·그룹핑·워드클라우드 같은 갈무리 방법을 비교·평가할 때 입력으로 쓴다. 생성 기준은 `SPEC.md`(권위 문서).
실명·실제 인물·실제 조직 내부 사실은 없고, 회사명은 "카뱅/카카오뱅크"만 쓴다. 464건 전부 사람이 손으로 쓴 문장이며 슬롯 채우기·템플릿 생성은 쓰지 않았다.

## 파일

| 파일 | 내용 |
|---|---|
| `answers.json` | 464건 `{team_id, item_id, body, label, submitted_at}`. 반조 순서 → 항목 순서로 정렬. 시각은 ISO 8601 `+09:00` |
| `personas.json` | 58개 반조 속성: `divisions`(2~3개), `ai_maturity`, `stance`, `tone`, `is_exec`, `members`(3 또는 4명) |
| `labels.json` | 항목별 라벨 정의·목표 비율·실제 건수(`items`), off-topic 답 목록(`offtopic`), 두 의견 병기 답 목록(`mixed`) |
| `board_wide_mock.csv` | 앱 와이드 내보내기와 같은 열(반조, 테이블, 임원테이블, Q1-1 … Q2-3b, 마지막제출시각). 58행. UTF-8 BOM · CRLF · RFC 4180 |
| `board_long_mock.csv` | 반조, 항목, 본문, 제출시각, hidden(false), 숨김사유(빈칸), 수정횟수(0), label. 464행. 같은 인코딩 규칙 |
| `validate.mjs` | 건수·라벨 비율·길이 분포·중복률·off-topic·금지어·예시 문장·시각·CSV 왕복을 검사하는 스크립트 (`node data/board_mock/validate.mjs`, 의존성 없음, `--dups`로 중복 판정 목록 출력) |
| `_gen/` | 재생성용 소스. `answers_src.mjs`(손으로 쓴 원문 + 짝짓기 태그), `build.mjs`, `spec.mjs`. 산출물만 쓸 때는 무시해도 된다 |

CSV의 시각은 앱 내보내기와 같이 `YYYY-MM-DD HH:mm:ss`(KST)로, JSON은 ISO 8601 `+09:00`으로 적었다. 두 값은 같은 시각이다.

## 라벨을 정답으로 쓰는 법

- 답변마다 주제 라벨(cluster) 1개가 붙어 있고, 이것이 **정답(ground truth)** 이다. 라벨 정의는 항목마다 SPEC §2 표 그대로이며 `labels.json`에 옮겨 두었다.
- 평가 방식 예: 그룹핑 알고리즘이 만든 묶음과 이 라벨을 비교해 순도(purity)·재현율·ARI/NMI를 낸다. 요약 방법은 라벨별 건수 비율을 얼마나 되찾는지, 소수 의견(예: `keep_manual`, `culture_fear`)을 놓치지 않는지로 본다.
- 라벨은 **항목 안에서만** 의미가 있다. 항목이 다르면 같은 이름의 라벨(`other`)도 서로 다른 묶음이다.
- 노이즈를 일부러 넣었으므로 정확도 100%는 기대하지 않는다. 노이즈 종류:
  - **중복(~8%)**: 같은 항목 안에 표현이 거의 같은 답(예: "주간보고 AI 초안부터"가 여러 반조). 동일 문장이거나 띄어쓰기·마침표만 다른 형태, 문자 바이그램 자카드 ≥ 0.8. 항목당 4~5건.
  - **살짝 빗나간 답(off-topic, ~4.7%, 22건)**: `labels.json > offtopic`에 목록이 있다. Q1-4에는 "퇴직연금 서비스 강화", "외환 서비스 확대" 같은 AI와 무관한 서비스 아이디어를 `offtopic_service` 라벨로 4건 넣었다(10/8 논의에서 실제로 나온 현상). 그 밖의 항목에서는 "재택근무 늘었으면", "주 4일 근무" 처럼 질문을 비껴간 답을 `other`로 두었다. Q1-1에는 off-topic 라벨이 없어 넣지 않았다.
  - **두 의견 병기(~2.6%, 12건)**: "A도 있고 B도 있다" 형태(그라운드 룰 ③). `labels.json > mixed`에 목록이 있고, 라벨은 먼저 나온(주된) 의견 하나만 붙였다. 평가 때 이 건들은 별도로 집계하거나 제외해도 된다.
  - **길이 편차**: 15자 미만 15% · 15~44자 45% · 45~89자 30% · 90~170자 10%(실측 15.7/45.7/28.7/9.9). 170자 초과 없음. 짧은 답이 많은 것은 폰으로 급히 친 말투를 흉내 낸 것이다.
- `other` 라벨(금융 교육·기록 보관·정서적 안정감 등)은 "남는 통"이라 알고리즘이 묶기 어려운 게 정상이다.

## 페르소나 설계

반조 단위 속성이며 **답변의 어휘·관점을 바꾸는 데만** 썼다. 본문에 부서명을 직접 쓴 답은 25건(약 5%).

- `divisions`: 여신 · 수신/예적금 · 플랫폼/제휴 · 데이터/AI · 리스크 · IT개발 · 인프라/보안 · 고객센터(CS) · 마케팅/브랜드 · 전략/재무 · 준법/감사 · 인사/조직 · 투자/신사업 · 해외(동남아) · UX/디자인 · 결제/카드 중 2~3개
- `ai_maturity`: low 15 / mid 26 / high 17 (26/45/29%) — low는 "프롬프트를 몰라서" 류, high는 "맥락 설계·에이전트 단계 분리" 류 어휘
- `stance`: optimistic 23 / cautious 23 / skeptical 12 (40/40/21%) — skeptical은 "큰돈은 직접", "AI 답은 참고만" 류
- `tone`: casual 26 / neutral 23 / formal 9 (45/40/16%)
- `is_exec`: 8A·8B·13A·13B·14A·14B·18A·18B. 이 반조들은 tone이 neutral/formal이고, 전략적·추상적 문장("위임의 범위가 커질수록 …", "~해야 한다고 본다")을 우선 배정했다.
- 짝짓기 방식: 항목마다 손으로 쓴 58개 답에 어조·입장·숙련도·부서 언급 태그를 달고, 반조 속성과의 적합도 점수를 헝가리안 알고리즘으로 최대화해 배정했다(시드 고정, 재현 가능). 태그는 산출물에 나가지 않는다.

## 제출 시각

SPEC §3 구간 안에서 반조별로 무작위. 각 항목마다 1~3개 반조는 마감 직전(마지막 ~20초)에 제출한다. Q2-3a와 Q2-3b는 반조별로 같은 시각이다.

## 재생성

```
node data/board_mock/_gen/build.mjs      # answers_src.mjs + SPEC.md → JSON·CSV 전부 다시 씀
node data/board_mock/validate.mjs        # 검사 (모두 통과해야 exit 0)
```

원문을 고칠 때는 `_gen/answers_src.mjs`만 수정한다(형식 `label|태그|본문`, 항목당 58줄). `build.mjs`가 라벨 id가 SPEC에 있는지 확인한다.
